2026年6月に追加された新しいHTTPメソッドです。

https://datatracker.ietf.org/doc/html/rfc10008

`GET`のように安全かつ冪等でありながら、`POST`のようにリクエストボディを持つことができるHTTPメソッドです。

## 比較

RFC10008で`GET`,`QUERY`,`POST`の3つのHTTPメソッドが比較されています。

| 項目 | GET | QUERY | POST |
| --- | --- | --- | --- |
| 安全 | はい | はい | いいえ |
| 冪等 | はい | はい | いいえ |
| クエリ自体のURI | はい（定義上） | オプション（位置情報応答フィールド） | いいえ |
| クエリ結果のURI | オプション（Content-Locationレスポンスフィールド） | オプション（Content-Locationレスポンスフィールド） | オプション（Content-Locationレスポンスフィールド） |
| キャッシュ可能 | はい | はい | はい、ただし今後のGETまたはHEADリクエストに限ります。 |
| コンテンツ（ボディ） | 「意味が定義されていない」 | 期待される結果（対象リソースごとの意味論） | 期待される結果（対象リソースごとの意味論） |

上の表から、下記のようなことがわかります。

- `QUERY`は、`GET`と同じく安全かつ冪等である。
- `QUERY`は、`POST`と同じくリクエストボディを持つことができる。
- `QUERY`は、`GET`と同じくキャッシュ可能である。

## 使いどころ

`QUERY`メソッドは、`GET`と同じく安全かつ冪等であり、`POST`と同じくリクエストボディを持つことができるため、検索やフィルタリングなどのクエリ操作に適しています。

## なぜGETやPOSTではなくQUERYなのか

例えば
```
/search?hoge=hogehoge&fuga=fugafuga&...
```

のように、検索キーワードをクエリパラメータとしてURLに含める場合、URLの長さ制限に引っかかる可能性があったり、URIに含まれる情報がログに残ってしまうなどの問題があります。また、ネストされた検索条件を表現しづらいという問題もあります。

`GET`でリクエストボディを持たせることは技術的には可能ですが、リクエストが失敗したり、拒否されたりしてしまうため、[RFC7231](https://datatracker.ietf.org/doc/html/rfc7231#section-4.3.1:~:text=GET%E3%83%AA%E3%82%AF%E3%82%A8%E3%82%B9%E3%83%88%E3%83%A1%E3%83%83%E3%82%BB%E3%83%BC%E3%82%B8%E5%86%85%E3%81%AE%E3%83%9A%E3%82%A4%E3%83%AD%E3%83%BC%E3%83%89%E3%81%AB%E3%81%AF%E3%80%81%E5%AE%9A%E7%BE%A9%E3%81%95%E3%82%8C%E3%81%9F%E6%84%8F%E5%91%B3%E3%81%AF%E3%81%82%E3%82%8A%E3%81%BE%E3%81%9B%E3%82%93%E3%80%82%0A%20%20%20GET%E3%83%AA%E3%82%AF%E3%82%A8%E3%82%B9%E3%83%88%E3%81%A7%E3%83%9A%E3%82%A4%E3%83%AD%E3%83%BC%E3%83%89%E3%83%9C%E3%83%87%E3%82%A3%E3%82%92%E9%80%81%E4%BF%A1%E3%81%99%E3%82%8B%E3%81%A8%E3%80%81%E6%97%A2%E5%AD%98%E3%81%AE%0A%20%20%20%E3%83%AA%E3%82%AF%E3%82%A8%E3%82%B9%E3%83%88%E3%82%92%E6%8B%92%E5%90%A6%E3%81%99%E3%82%8B%E5%AE%9F%E8%A3%85%E3%80%82)でも`GET`メソッドにリクエストボディを持たせることは推奨しないと明記されています。

上記の対応として、`POST`メソッドを使うこともできますが、状態を変更するリクエストではないため、`POST`メソッドを使うのは適切ではありません。

また、`POST`メソッドだと、キャッシュが効かないため、検索結果のキャッシュを有効にしたい場合には不向きという問題もあります。

## 検証

### 前提条件

- Node.js v26.5.1
- Bun v1.4.0
- Hono v4.13.5

v4.13.0から、Honoで`QUERY`メソッドを使えるようになっていることは確認済みです。

https://github.com/honojs/hono/releases/tag/v4.13.0

### サーバー側

デフォルト生成の`src/index.ts`を以下のように編集します。

```ts
import { Hono } from 'hono'

const app = new Hono()

app.query('/search', async (c) => {
  const query = c.req.query()
  const body = await c.req.json()
  return c.json({ query, body })
})

fire(app);
```

`c.req.query()`だけでなく`c.req.json()`でリクエストボディも読み取り、レスポンスに含めています。これによって、`QUERY`メソッドが`GET`のようにクエリパラメータを扱いつつ、`POST`のようにリクエストボディも持てることを確認できます。

### クライアント側

`curl`で`QUERY`メソッドを指定し、リクエストボディを付けてリクエストを送ります。

```sh
curl -X QUERY 'http://localhost:3000/search?hoge=hogehoge' \
  -H 'Content-Type: application/json' \
  -d '{"fuga":"fugafuga"}'
```

実行すると、以下のようにクエリパラメータとリクエストボディの両方がレスポンスに含まれていることが確認できました。

```json
{
  "query": { "hoge": "hogehoge" },
  "body": { "fuga": "fugafuga" }
}
```

これによって、`QUERY`メソッドが`GET`のようにクエリパラメータを扱いつつ`POST`のようにリクエストボディを持てるという、比較表で挙げた特徴を確認することができました。

## まとめ

正式な策定からまだ日が浅く、すべてのフレームワーク・ライブラリが`QUERY`メソッドをサポートしているわけではないので、しばらく静観の必要がありそうですが、今後の検索やフィルタリングなどのクエリ操作においては、`QUERY`メソッドを採用することになりそうです。
